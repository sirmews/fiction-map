# Decision: Derived Unlock Semantics

**Date:** 2026-05-18
**Status:** Superseded in part by the Task 6 implementation (commit `438d95e`, 2026-05-18). See [Update](#update-2026-05-18-post-task-6) below.

## Context

The engine maintains two sets of entity states:
1. **Runtime State (`EntityRuntimeState`)**: The explicit, mutable, serializable state (e.g., `owned`, `active`, `unlocked` arrays/sets).
2. **Derived State (`DerivedEntityState`)**: The read-only state generated by `deriveEntityState(world, state)`, which computes a unified view of what's effectively active based on static entity schemas (`references`, `unlocks`) and the player's explicit runtime progress.

A tension exists around "unlocks".
*   In the `literature-rpg.test.ts` example, acquiring the "Lantern" *statically* implies the "Dark Cave" should be unlocked (via the `unlocks: ["dark-cave"]` schema on the Lantern).
*   The historical built-in evaluators (`entityUnlockedEvaluator`, `hasEntityEvaluator`, `entityActiveEvaluator`) read exclusively from the explicit *Runtime State*. They did not evaluate against the *Derived State*.
*   Therefore, an author defining an `unlocks` cascade on an entity did not automatically grant the ability to traverse transitions gated by `entityUnlocked` conditions unless the consumer app intercepted this and explicitly mutated `EntityRuntimeState` by calling `unlockEntity`.

## Decision (original)

**Keep derived unlocks strictly read-only. Do not silently merge derived unlocks into the runtime state during condition evaluation or graph traversal.** Plan an explicit `materializeDerivedState(state, derivedState)` helper as a follow-up.

## Rationale (original)

1. **Separation of Concerns (Pure Evaluation):** Condition evaluation should remain fast and predictable, reading only from explicitly persisted state.
2. **Author Intent vs System State:** A consumer app may want to animate unlocks, show a modal, or run special effects when a derived unlock is "discovered." Silent promotion to runtime state would deny the consumer that observation point.
3. **Ergonomic Gap:** Forcing the consumer to write a loop translating `derived.effectiveEntityIds` back into `unlockEntity(state, id)` is tedious — flagged as a known cost.

## Update (2026-05-18, post-Task 6)

The follow-up `materializeDerivedState` helper was **not** implemented. Instead, Task 6 of the [engine-ergonomics plan](../superpowers/plans/2026-05-18-engine-ergonomics.md) (commit `438d95e`) resolved the ergonomic gap a different way:

- `EvaluationContext` gained an optional `derivedState?: DerivedEntityState` field.
- `checkTransitionAvailability` and `applyTransition` now accept that context as an additional argument.
- The entity-aware built-in evaluators (`entityUnlockedEvaluator`, `hasEntityEvaluator`, `entityActiveEvaluator`) check `context.derivedState.effectiveEntityIds` first and fall back to explicit runtime state.

This **preserves both invariants from the original rationale**:
- **Pure evaluation:** the engine never mutates runtime state. Derived state is recomputed by the consumer and passed in.
- **Author intent:** the consumer chooses when to derive and pass `{ derivedState }`. If they want a strict, runtime-only check (e.g. for save-game validation), they simply omit the context.

What changed is the *interface*: derived unlocks are now respected by the engine when the consumer opts in via the evaluation context, instead of through an explicit state-mutating helper.

The [literature-rpg.test.ts example](../../packages/story-runtime/src/examples/literature-rpg.test.ts) demonstrates the full flow: the Lantern's `unlocks: ["dark-cave"]` is honored by `checkTransitionAvailability` without anyone ever calling `unlockEntity(state, "dark-cave")`, and `entityIsUnlocked(state, "dark-cave")` correctly remains `false` afterwards.

## Story Editor Implications

For a Story Editor consumer:
*   Compute `deriveEntityState(world, state)` once per render/decision tick.
*   Pass `{ derivedState }` to `checkTransitionAvailability` / `applyTransition` whenever cascading unlocks should be respected.
*   Skip passing it when running strict runtime-only checks (e.g. validating a save file in isolation).
*   No explicit "materialize" step is required to make the cascade work at runtime.
