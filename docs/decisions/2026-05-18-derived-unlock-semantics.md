# Decision: Derived Unlock Semantics

**Date:** 2026-05-18

## Context

The engine currently maintains two sets of entity states:
1. **Runtime State (`EntityRuntimeState`)**: The explicit, mutable, serializable state (e.g., `owned`, `active`, `unlocked` arrays/sets).
2. **Derived State (`DerivedEntityState`)**: The read-only state generated by `deriveEntityState(world, state)`, which computes a unified view of what's active based on static entity schemas (`references`, `unlocks`) and the player's explicit runtime progress.

A tension exists around "unlocks". 
*   In the `literature-rpg.test.ts` example, acquiring the "Lantern" *statically* implies the "Dark Cave" should be unlocked (via the `unlocks: ["dark-cave"]` schema on the Lantern).
*   However, our runtime condition evaluators (like `entityUnlockedEvaluator`) read exclusively from the explicit *Runtime State*. They do not evaluate against the *Derived State*.
*   Therefore, an author defining an `unlocks` cascade on an entity doesn't automatically grant the ability to traverse transitions gated by `entityUnlocked` conditions, unless the consumer app intercepts this and explicitly mutates the `EntityRuntimeState` by calling `unlockEntity`.

## Decision

**We will keep derived unlocks strictly read-only and *will* introduce an explicit state materialization helper in the next phase.**

We will *not* silently merge derived unlocks into the runtime state during condition evaluation or graph traversal.

## Rationale

1. **Separation of Concerns (Pure Evaluation):** Condition evaluation should remain fast and predictable, reading only from explicitly persisted state. If evaluation required re-running full graph derivation on every check, performance could degrade.
2. **Author Intent vs System State:** A consumer application might want to animate unlocks, show a modal, or run special effects when a derived unlock is "discovered." If the engine silently treats derived unlocks as true runtime unlocks, the consumer app loses the opportunity to observe the state change.
3. **Ergonomic Gap:** We acknowledge that forcing a consumer app to write the loop that translates `derived.effectiveEntityIds` or `derived.unlocks` back into `unlockEntity(state, id)` is tedious. 

## Next Steps

To resolve the ergonomic gap without violating our state separation rules, we will add a new task to our implementation backlog: **Materialize Derived Unlocks Helper**. 

This helper will be an explicit function (e.g., `materializeDerivedState(state, derivedState)`) that a consumer app can call to safely promote derived unlocks into hard, serializable runtime unlocks at a time of their choosing (usually right before saving the game or rendering the UI).

## Story Editor Implications

For a Story Editor consumer:
*   The editor's "Play Mode" must explicitly invoke this new helper if it wishes cascaded entity unlocks to be respected by runtime transition gates.
*   The editor has full control over *when* to apply this, allowing it to hook into UI notifications before committing the state changes.
